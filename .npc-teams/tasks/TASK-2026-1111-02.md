## [卡-20261111-03] 局部类型挡住包级新函数时，提升类型而非把逻辑塞回函数内
- 症状：恢复的解析器是包级函数，编译报 `undefined: ruleWithUpstreams / lbRule / upstream`——

  只在该函数可见的其它局部类型（此时需连带提升或用最小接口替代）。

### 7.4 遇到的问题

1. **主模块物理上没有 caddy 依赖**——这是 P1-1 的硬约束，不是我的取舍。探针实测报 `no required module provides package github.com/caddyserver/caddy/v2`。若要在 `internal/services` 内跑解码，必须给主模块加 caddy 依赖（会污染后端构建面与依赖树，风险远大于收益），故改为「生成侧在本模块、解码侧在 caddygeoip、同一份产物串联」。
2. **`json.RawMessage` 的静默短路**：`Routes []json.RawMessage` 会让整个结构体解析成空（RawMessage 自身实现 Unmarshaler），实测 `servers=0`。改为 `map[string]map[string]json.RawMessage` 逐层取。
3. **`ctx.LoadModuleByID` 与 `Route.Provision` 语义差异**：直接调 `LoadModuleByID` 不会剥离 `"handler"` 键，报 `json: unknown field "handler"`。`Route.Provision` → `ctx.LoadModule(r,"HandlersRaw")` 才剥离。故主路径改为**先跑真实 `Provision`**，仅在失败时逐 handler 归因（归因时自行剥离 `handler` 键）。
4. **`Handlers` 可能多于 `HandlersRaw`**：`static_response` 这类内建快捷形态由 `Route.UnmarshalJSON` 预置，不走 `HandlersRaw`。断言从 `!=` 改为 `<`（只要求「没有 handler 丢失」）。

  把 resolver 层的错误值掩盖成相同产物——两层冗余回退使"只断言产物"不可区分。
- 判据：改坏一处生产代码后，相关用例必须变红；若不变红，说明该用例根本没覆盖到那处代码。
  命令形态：改 → go test -run <相关> → 必须 FAIL → git checkout 还原。
- 解法：对每一层各自断言（resolver 层断派生值、渲染层断产物），并在注释里写明
  "本用例测 X 层，Y 层由 Z 用例覆盖"。三次变异（禁用 hoisted / 删第二档 / orphan 空）
  分别捕获 6 / 3 / 1 条用例。
- 适用条件／不适用面：适用于任何"生产代码 + 测试"配对；不适用于纯文档/配置改动。
- 复发：首次。

## [卡-20261111-06] 跨模块测试边界由 go.mod 决定，不由目录结构决定
