### 7.6 经验卡

```
## [卡-20261111-03] 局部类型挡住包级新函数时，提升类型而非把逻辑塞回函数内
- 症状：恢复的解析器是包级函数，编译报 `undefined: ruleWithUpstreams / lbRule / upstream`——
  这三个类型是 `generateCaddyConfigFromStore` 的函数内局部类型。
- 根因：局部类型只在该函数作用域可见；新解析器写在包级（测试与多入口复用需要）就必然失配。
- 判据：`go build ./...` 报 `undefined: <类型名>`，而 `grep "type <名> struct"` 只在函数体内命中。
- 解法：类型定义**逐字**提升到包级（仅去掉一层缩进），并在类型上方注明「原为函数内局部类型，
  因 X 需包级可见性提升，定义体未变」。禁止把整段渲染逻辑搬回那个大函数里凑作用域。
- 适用条件／不适用面：适用于「函数内局部类型 + 新增包级消费者」；不适用类型本身持有
  只在该函数可见的其它局部类型（此时需连带提升或用最小接口替代）。
- 复发：首次。
```

```
## [卡-20261111-04] 结构性代码编辑禁用正则批量改写：字段字面量转赋值会毁语法
- 症状：为把 `SingleRuleConfig{Field: v}` 批量改成 `rule.Field = v`，用正则处理测试文件，
  产出 `rule.CustomRoutesEnabled = true,` / `rule.{Host = ...}` 一类非法行，`go vet` 报
  `expected '==', found '='` 十余处，且嵌套的 `PathRules: []PathRuleConfig{{` 被切断。
- 根因：Go 复合字面量是嵌套结构（含 `{{`、跨行、内部还有字面量），正则按行处理必然
  在嵌套边界失效——与「文本并集破坏语法」同类（见 卡-20261110-02）。
- 判据：`gofmt -e <file>` 退码非 0 / `go vet` 报 `expected '=', found ...`，且行文本里出现
  `rule.{` 或「赋值为字面量的字段」形态。
- 解法：**结构性编辑逐个手工 `replace_in_file`**；确需批量时按「括号配对 + AST」处理，
  或先 python 定位精确行号再做**行级**替换（`lines[i:j] = new_lines`）并立即 gofmt+vet 验证。
- 适用条件／不适用面：适用于 Go/TS 等有嵌套字面量的源码；不适用纯文本配置/文档批量替换。
- 复发：首次（与 卡-20261110-02 同族：该卡讲合并并集，本卡讲单文件改写）。
```
