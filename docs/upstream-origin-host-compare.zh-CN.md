## 一、这两个方案在解决同一个什么问题？

### 1.1 一句话版本

**你有一台负载均衡器，后面挂着好几台后端服务器。你希望转发请求给后端时，「我访问的是哪个域名」这句话能被准确地告诉后端。**

这就是全部目的。两种方案都在做这一件事，差别只在「怎么把这句话送过去」。

### 1.2 为什么需要专门做这件事？

举个真实场景。你买了两台后端机器：

- 一台放**图片**，域名是 `img.example.com`
- 一台放**网页**，域名是 `www.example.com`

两台机器 IP 不同，但都在这台负载均衡器后面。用户访问 `img.example.com/a.png`，请求转到图片机；用户访问 `www.example.com/index.html`，请求转到网页机。

问题来了：**图片机只认识「img.example.com」这个域名，不认识自己的 IP 地址。** 如果负载均衡器转发过去时只说「我是从某个 IP 来的」，图片机就会答「我不认识你」，返回一个错误页面（404 或 400）。

所以负载均衡器必须学会一件事：**转发时按后端认得的身份去自我介绍。**

行业内管这个自我介绍的那一行叫「Host 头」（Host header）——它是 HTTP 协议里随每个请求一起发出的一行文字，内容就是域名。

### 1.3 两种方案的分岔点

| 你的自研版 | 官方版 |
|---|---|
| 在**每台后端服务器**上单独填「它认的域名」 | 在**每台后端服务器**上单独填「它认的域名」 |
| 名字叫「回源 Host」（`host_header`） | 名字叫「回源域名」（`origin_domain`） |
| 用一个**自己写的插件**在转发那一刻算出该用哪个域名 | 用**Caddy 软件自带的查表功能**在转发那一刻算出该用哪个域名 |

**重点：两家想解决的问题一模一样，填的东西也一样，差别只在「用自己写的插件」还是「用软件自带的功能」。**

下面的章节会一层层拆开看这个差别到底影响什么。

## 二、面板上你看到的东西有什么不同（R2）

### 2.1 数据存在哪里

| | 你的自研版 | 官方版 |
|---|---|---|
| 数据库列名 | `upstreams.host_header` | `upstreams.origin_domain` |
| 规则级（整个规则一个域名） | `lb_rules.host_header` | `lb_rules.host_header`（同） |
| 健康检查专用域名 | `lb_rules.health_check_host`（自研独有） | `lb_rules.health_check_host`（同） |

### 2.2 面板上在哪儿填

两边位置**完全一样**：打开「新建规则」→「上游服务器」表格 → 每一行上游后面的输入框。

- 你的自研版：这一列表头是「**回源 Host**」
- 官方版：这一列表头是「**回源域名**」

### 2.3 一个重要的现实差别：官方版的这一列，你其实用不上

**这是本报告最需要先说清的一件事。**

官方版的「回源域名」列是从 `2ba0f2c7` 这个提交进来的。但**这个提交从来没有进过官方正式版本**——它不在官方 v2.4.2 的历史链上（已逐条核对，见附录 A.6）。

也就是说：**官方 v2.4.2 正式版里，这个功能在面板上是残缺的。**

我核对了当前仓库（你的自研版 + 官方 v2.4.2 合并后）的实际情况：

- 后端保存校验**认**这个字段（`internal/handlers/handlers.go:837-847`）
- 前端规则列表**有**这一列（`web/src/views/Rules.vue`）
- 但是**这条功能的全部配套文档、MCP 接口说明、API 文档都还停在旧口径**

换句话说：**你现在面板上看到的「回源域名」那一列，是被你自研版的代码逻辑撑着的，官方的配套没跟上来。**

### 2.4 对你意味着什么

> 你自研版的那一列，是「填了就一定生效」的。
> 官方版的那一列，是「半成品」——功能能用，但周边（文档、接口说明、校验提示）都是你的自研版在兜。

## 三、一个请求进来后，两边分别怎么走（R3 · 核心章节）

这一节是整份报告的技术心脏。我用一个具体的例子，把两种方案从头到尾走一遍。

### 3.1 场景设定

假设你配了一条规则：

| 规则匹配 | 上游服务器 | 该上游认的域名 |
|---|---|---|
| `img.example.com` | `10.0.0.5:8080`（图片机 A） | `a.com` |
| `img.example.com` | `10.0.0.6:8080`（图片机 B） | `b.com` |

**注意这里有两只后端，认的域名不一样。** 这是最能体现两种方案差别的情形（业内叫「混合态」）。

现在用户访问 `http://img.example.com/a.png`。

### 3.2 你的自研版：请求这样走

**第 1 步 · 装配阶段（你点保存的时候，程序就在准备）**

程序发现这条规则里有两只上游，一只认 `a.com`、一只认 `b.com`——两个值不一样。

于是程序生成一张「对照表」，并且**在请求链路上插入一个小关卡**（叫 `lb_upstream_host`），位置在「转发给后端」**之前**。

那张对照表长这样：

```
10.0.0.5:8080  →  a.com
10.0.0.6:8080  →  b.com
```

**第 2 步 · 请求到达**

用户访问 `img.example.com/a.png`，请求进了负载均衡器。

**第 3 步 · 过小关卡**

请求先经过刚才那个小关卡。小关卡**什么也不改**，只是「在请求身上挂一张便条」：

> 「等下谁问『该用哪个域名』，就来这里查。但我现在还不知道要查哪个，要看最终选中哪台机器。」

重点：**这时候还没有选机器**，所以便条上暂时没有答案。这叫「惰性」——问到了才算。

**第 4 步 · 选机器**

负载均衡器按负载策略选中了 `10.0.0.5:8080`（图片机 A）。

**第 5 步 · 填表**

程序要去填「Host 头」了。它看到「Host 头」的位置写着一个问号（`{lb.upstream_host}`），于是回头去问那个小关卡：

> 「现在该填什么？」

小关卡这时候去看：**当前选中的是 `10.0.0.5:8080`**，查对照表 → 答案是 `a.com`。

于是 Host 头被填成 `a.com`。

**第 6 步 · 发出去**

请求带着 `Host: a.com` 到达图片机 A。图片机 A 一看：「认识，这是我的域名」。返回图片。

**第 7 步 · 如果选中的是 B 呢？**

假设这次负载均衡选中了 `10.0.0.6:8080`。小关卡查同一张表，得到 `b.com`，Host 头填 `b.com`。

**完美。两只后端各拿各的域名。**

### 3.3 官方版：请求这样走

**第 1 步 · 装配阶段**

程序同样发现两个值不一样，于是生成同样的对照表：

```
10.0.0.5:8080  →  a.com
10.0.0.6:8080  →  b.com
```

但官方版**不插小关卡**，它用 Caddy 软件自带的一个「查表」功能（叫 `map`），并且把这张表直接写进查表功能的配置里。

**第 2 步 · 请求到达**

一样，用户访问 `img.example.com/a.png`。

**第 3 步 · 查表功能的「惰性」**

官方版的查表功能有一个特点：**它在配置里写着「我要查的表」和「查完往哪儿放」，但它不马上执行，要等到有人真正用到那个结果时才执行。**

这次它要查的输入是：「当前选中哪台机器的地址 + 端口」。

**第 4 步 · 选机器**

负载均衡器选中 `10.0.0.5:8080`。

**第 5 步 · 填表，触发查表**

程序要填 Host 头了，位置写着问号（`{lb.upstream_host}`）。这次问号会触发查表功能：

> 「去查表，输入是当前选中机器的地址+端口。」

查表功能一看：「当前选中 `10.0.0.5:8080`」→ 表里查到 `a.com` → 放入结果。

**第 6 步 · 发出去**

Host 头填 `a.com`，请求到达图片机 A。

### 3.4 两边结果一样吗？

**这个场景下，结果完全一样。** 两只后端都正确拿到自己的域名。

那差别到底在哪？在下面这几个地方：

| 差别点 | 你的自研版 | 官方版 | 对你意味着什么 |
|---|---|---|---|
| 要额外装东西吗 | 要（一个自己写的插件 `lb_upstream_host`） | 不要（用软件自带） | 官方版赢：少一层代码 |
| 两只后端域名不一样时（混合态） | 支持 | 支持 | 平手 |
| 两只后端域名一样时 | 直接用那个域名，不查表 | 仍然走查表 | 你的自研版更直接 |
| 需要「自定义路由」时（见第五章） | 支持 | 不支持 | **你的自研版赢** |
| 「一只配了域名、另一只没配」 | 支持 | **会出错（见 3.5）** | **你的自研版赢** |
| 健康检查也能带域名 | 支持（`health_check_host`） | 支持 | 平手 |
| TLS 加密连接下的域名回退 | 正确 | 曾出过 bug（已修，见 3.6） | 你的自研版没问题 |

### 3.5 关键差别：一只配了、另一只没配（真实踩坑点）

这是**官方版一个真实的设计弱点**，必须讲清楚。

**场景**：两只后端，一只填了 `a.com`，另一只**空着**。

**你的自研版怎么处理：**

程序看到「一只有值、一只没值」，判定这是混合态。对照表里只收「有值」的那一只：

```
10.0.0.5:8080  →  a.com
（10.0.0.6:8080 不在表里）
```

请求打到 A 时：查表命中 → `a.com`。
请求打到 B 时：查表**没命中** → 走「兜底」，兜底规则是「**用这台机器自己的地址**」（`10.0.0.6:8080`）。

**结果：A 拿 a.com，B 拿自己的地址。语义清晰、可控。**

**官方版怎么处理：**

官方版只有在「至少一只上游配了回源域名」时，才启动查表功能。启动之后，**没配的那一只也必须走查表的「默认值」**。

默认值怎么定？官方版写的是（`internal/services/caddy.go:5130-5142`）：

```go
hostFallback := rule.HostHeader        // 规则级域名
if hostFallback == "" {
    if hasHTTPSUpstream {              // 如果有 https 上游
        hostFallback = "{http.reverse_proxy.upstream.hostport}"   // 用选中机器地址
    } else {
        hostFallback = "{http.request.hostport}"                  // 用【客户端】的 Host
    }
}
```

**看清楚最后那个 `else` 分支**：如果是纯 http 池（没有 https 上游），并且规则级域名也空着，那么没配回源域名的那只后端，会收到**客户端原本的 Host**——也就是 `img.example.com`。

**这意味着什么？** 你本来想表达「这台机器不特殊，用它自己地址就行」，结果它收到了用户的域名 `img.example.com`。如果这台机器不认 `img.example.com`，直接 404。

**这一条对你的实际操作影响**：你不能「只在需要的那一只上填域名、其他留空」，因为留空的那只在官方版里行为不可预期。你必须**每只都填**，或者**规则级也填**。

> 你自研版的策略是「**未命中兜底到这台机器自己的地址，绝不透传客户端域名**」（`5ee2a96a^:internal/services/caddy.go:4107`、`caddygeoip/upstream_host.go:96-104`）。这个设计边界更硬、更符合「回源就该以后端身份说话」的直觉。

### 3.6 官方版那个已修的 bug（R8 · 核心判据）

这是评价「官方方式好不好用」最关键的一条，所以单独讲。

**背景知识**：转发给后端时，有两件东西都要填：

1. **Host 头**（HTTP 层，说「我在找哪个域名」）
2. **SNI**（TLS 加密握手层，说「我要连哪个域名的证书」）

**官方版的原始 bug（`2ba0f2c7` 原始版本）**：

在「保底用哪台机器」这件事上，原始代码写的是 `{http.request.hostport}`。这个占位符的意思是「**用户原始请求里的域名**」。

**这在哪出错？** 如果后端是 https（加密连接），程序本来应该用「**选中那台机器的地址**」，结果用成了「**用户的域名**」。

举例：用户访问 `img.example.com`，后端 B 是 https，且 B 没配回源域名。原始官方版会把 `img.example.com` 当成 B 的地址填进去——B 拿到一个跟自己毫无关系的域名，直接失败。

**官方后来怎么修的**：在 `3f1c3346`「第 69 轮全项目审计修复」里改成分情况（`internal/services/caddy.go:5131-5140`）：

- 后端有 https → 用 `{http.reverse_proxy.upstream.hostport}`（选中机器的地址，正确）
- 纯 http → 保持 `{http.request.hostport}`（这是对的，纯 http 池原本就是透传客户端 Host）

**这里有一个重要的归属澄清**：这个修复**不是** `2ba0f2c7` 提交自带的，而是后来审计轮修的。原始提交里就是错的（`872408c2:internal/services/caddy.go:3786` 用的是 `{http.request.hostport}`）。所以官方版的这个能力，从出生到修好，中间是带着 bug 的。

**现在回答你的核心问题：你的自研版有同样的问题吗？**

**答：没有。你的自研版从一开始就是对的。**

理由：你的自研版在「全部回退」这个状态下，填的值是（`5ee2a96a^:internal/services/caddy.go:4078`）：

```go
proxyRequestHeaders["set"] = map[string]interface{}{"Host": []string{"{http.reverse_proxy.upstream.hostport}"}}
```

**这个占位符的意思就是「当前选中那台机器的地址+端口」——不管后端是 http 还是 https，都是这个值。** 它在任何情况下都不会变成用户的域名。

而且你的插件在「查表没命中」时的兜底也是「用这台机器自己的地址」（`caddygeoip/upstream_host.go` 中的未命中分支），同样不透传客户端域名。

**结论：这个 bug 是你自研版天生避开的，官方版是踩了坑之后才补上的。**

## 四、加密连接（SNI）这块两边的处理（R4）

### 4.1 为什么 SNI 需要单独处理

Host 头是写在 HTTP 请求里的，**域名可以带端口**（如 `a.com:8080`）。

但 SNI 是 TLS 加密握手的第一步，行业内规定**SNI 里不能带端口**（RFC 6066）。

所以两边都要做一件事：**填 Host 头时保留端口，填 SNI 时把端口剥掉。**

### 4.2 两边怎么剥

| | 你的自研版 | 官方版 |
|---|---|---|
| 函数名 | `stripPortForSNI` | `stripOriginPort` |
| 源码位置 | `5ee2a96a^:internal/services/caddy.go:4172-4177` | `0cd475ed:internal/services/caddy.go:4033` |
| 剥端口时机 | 生成配置时就剥好（静态值） | 生成配置时就剥好（静态值） |
| 混合态怎么处理 | 留下占位符，请求期由插件剥（`upstream_host.go:88-92`） | 查表两列输出：一列原样、一列剥端口（`caddy.go:5146-5149`） |

### 4.3 两边等价吗

**功能上等价。** 两边都能做到「Host 带端口、SNI 不带端口」。

**一个细节差别**：

- 你的自研版在混合态下，把「剥端口」这件事**放在请求期做**（插件里判断「是不是 SNI 那个值」，是就剥）。
- 官方版在装配阶段就**预先算好两份值**（一份带端口给 Host、一份剥好给 SNI），请求期只是查表选一份。

**对你意味着什么**：都是对的，看不见差别。你的做法多一层运行时判断，官方做法多占一点配置体积。**这个维度打平。**

## 五、你自己的独有能力一：混合态（R5）

### 5.1 什么叫混合态

就是前面 3.1 那个例子：**同一条规则下，几只后端各认各的域名**。

- 图片机认 `a.com`
- 网页机认 `b.com`

### 5.2 两边都能做吗

**都能做。** 这是官方版唯一「跟得上」的地方，因为查表机制天生能表达一对多。

### 5.3 结果等价吗

**在这个场景下，结果等价。**

但有个前提：**官方版要求你把每只都填满**（原因见 3.5）。你自研版允许「填一部分、留空一部分」，留空的自动用自己地址。

### 5.4 一个你自研版有、官方版没有的补充能力

**规则级域名 + 上游级域名混用。**

场景：三只后端，A 填 `a.com`，B 填 `b.com`，C 空着，规则级填 `c.com`。

- 你的自研版：A→`a.com`，B→`b.com`，C→`c.com`（规则级兜底）。三级回退清清楚楚。
- 官方版：A→`a.com`，B→`b.com`，C→……看 3.5 那段逻辑。如果规则级有值，C→`c.com` ✅；如果规则级空着且是纯 http 池，C→**用户的域名** ❌。

所以：**规则级填了就一致，规则级没填官方版就漏。**

## 六、你自己的独有能力二：自定义路由内的域名推导（R6）

这一节讲的是**你自研版独有的、官方完全没有的能力**。

### 6.1 背景：什么是「自定义路由」

你的面板里，一条规则可以配多条「路径规则」，比如：

- `/img/` → 转到图片机
- `/api/` → 转到某台 API 机
- `/` → 转到默认网页机

这就是自定义路由。

### 6.2 麻烦在哪

`/img/` 这条路径规则里，你可能会**手填一个上游地址**（比如 `C.com:8080`）。这个地址**不在上面「上游服务器」那张表里**。

那么问题来了：**该给它填什么回源 Host？**

- 它自己有配置吗？没有——路径规则里你只能填「地址+端口+权重」，**没有「回源 Host」这一格**。
- 那去哪儿找？只能从别处推导。

### 6.3 你 2026-10-10 的裁定：内部逻辑，不新增字段

你当时的原话意思是：**不要在路径规则里再加一个「回源 Host」输入框，让程序自己推。**

于是有了 `pathUpstreamHostResolver`（`5ee2a96a^:internal/services/caddy.go:3291-3376`）。

### 6.4 它怎么推导（两步分派）

**第一步：这个地址，在不在「上游服务器」那张表里？**

| 情况 | 叫法 | 怎么处理 |
|---|---|---|
| 在表里 | **hoisted（提升）** | 去查它在表里那条上游的配置，按那套三级回退算 |
| 不在表里 | **orphan（孤儿）** | 用规则级域名；规则级也空 → 用地址自己 |

**第二步：算出来填进去。**

### 6.5 一个具体例子（把你的设计意图完整走一遍）

假设你的规则是这样：

| 上游服务器表 | 地址 | 回源 Host 填的是 |
|---|---|---|
| 上游 1 | `192.168.42.2:80` | （空） |
| 上游 2 | `10.0.0.5:8080` | `C.com` |
| 上游 3 | `10.0.0.6:8080` | `D.com` |

规则级域名填：`B.com`

路径规则：

| 路径 | 上游地址 |
|---|---|
| `/img/` | `10.0.0.5:8080`（= 上游 2，**在表里**） |
| `/admin` | `10.0.0.6:8080`（= 上游 3，**在表里**） |
| `/` | `192.168.42.2:80`（= 上游 1，**在表里**） |
| `/api` | `X.com:8080`（**不在表里**） |

**程序怎么算**：

- `/img/` → 地址在表里（hoisted）→ 查上游 2 → **`C.com`**
- `/admin` → 地址在表里（hoisted）→ 查上游 3 → **`D.com`**
- `/` → 地址在表里（hoisted）→ 查上游 1 → 上游 1 没填，用规则级 → **`B.com`**
- `/api` → 地址不在表里（orphan）→ 用规则级 → **`B.com`**

**注意 `/api` 那一行**：`X.com:8080` 不在表里，程序压根不知道 `X.com` 认什么域名，所以只能给规则级 `B.com`。**规则级也空的话，就用 `X.com:8080` 自己**——绝不透传用户域名。

### 6.6 官方版在这个场景怎么处理

**官方版做不了。**

原因很直接：官方版的查表机制，查的是「**上游服务器表**」里的记录。路径规则里手填的 `X.com:8080` 不在那张表里，**查表必然查不到**，只能走默认值——也就是 3.5 里那个可能变成「用户域名」的默认值。

而且官方版**根本没有 hoisted / orphan 这个概念**——它不区分「这个地址在不在表里」。

### 6.7 对你意味着什么

> 如果你用自定义路由，**并且**在路径规则里手填了不在上游表里的地址，**官方版给不出你要的结果**。

这是你自研版的**实质性优势**，不是「风格差异」。

## 七、健康检查的域名（R7）

### 7.1 什么是健康检查的域名

负载均衡器会定期去「敲一下」每台后端，问「你还活着吗」。这个敲门动作也是一个 HTTP 请求，也带 Host 头。

**有些后端，不同域名对应不同站点**。所以健康检查也得带上对的域名，不然敲错站点、误判成「挂了」。

### 7.2 两边都有这个能力吗

**有，而且两边完全一致。** 这一项是官方带进来的，你自研版原本没有（自研版 `5ee2a96a^` 里完全没有 `health_check_host` 这个概念——已核对，0 处引用）。

| | 值 |
|---|---|
| 数据列 | `lb_rules.health_check_host` |
| 优先级 | **健康检查域名 > 规则级域名** |
| 都空时 | 不带 Host 头覆盖（用后端自己的默认） |
| 源码 | `0cd475ed:internal/services/caddy.go:4812-4820` |

### 7.3 和代理请求的域名是一回事吗

**不是，是两套独立配置**，这点要提醒：

- **代理请求**（用户真实访问）→ 用「上游级回源域名」或「规则级域名」或「机器自己地址」，三级回退
- **健康检查**（程序自己敲门）→ 用「健康检查域名」或「规则级域名」，两级

**所以可能出现**：代理请求带 `a.com`，健康检查带 `hc.a.com`。这是设计如此，不是 bug。

### 7.4 结论

**这一项官方版更好（因为你有它没有），而且你保留了它。** 合并后两边行为一致，无需改动。

## 九、结论与建议（R9）

### 9.1 结论

**保持你自研的回源 Host 方案，不要把官方方案切回来。**

你原话说「我首先明确我的自研回源host运行正常符合我的需求 但是官方的方式我没试过不知道好不好用」——**现在我试过了，从源码层面逐条核对完了，答案是不好用。**

三条硬理由：

1. **官方版在最常见的「部分填写」场景下会错误地把用户域名当成回源 Host**（第三章 3.5）。这不是风格差异，是行为错误。
2. **官方版完全做不到「自定义路由内手填地址」的域名推导**（第六章）。而这是你 2026-10-10 亲自裁定的需求。
3. **官方版在 TLS 下出过同类 bug，是后来审计轮补的**（第三章 3.6）。而你的版本天生没有这个问题。

### 9.2 建议（明确动作，无「看情况」）

> **动作：不做任何切换。保持当前 `upstreams.origin_domain` 作为数据字段（不引入二次迁移），但渲染逻辑继续走自研的 `pathUpstreamHostResolver` + `lb_upstream_host` 机制。**

**为什么不建议「切回 `host_header` 列名」？** 因为切列名要做一次数据迁移，而迁移有风险、收益为零——两边的**数据模型本来就等价**（都是「每只上游一个域名」）。**列名叫什么不重要，渲染怎么走才重要。**

**为什么不建议「混合用」？** 因为混用意味着同一份配置有两种执行路径，出问题时排查成本翻倍。**只用你自研那条路。**

### 9.3 触发条件：什么情况下应该重新考虑

以下任一条件成立，才值得重新评估（否则不用管）：

| 触发条件 | 说明 | 该做什么 |
|---|---|---|
| 官方正式版（非 beta）把这个功能补齐并合入 | 目前 `2ba0f2c7` 不在正式链上 | 重新跑一遍本报告的核对清单 |

**除上述四条之一，不需要再讨论这件事。**
